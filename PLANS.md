# Повторяемый процесс разработки

Это соглашение репозитория, а не специальная команда Codex. AGENTS.md указывает, когда его применять. План конкретного проекта каждый раз будет отличаться, но Codex составляет и обновляет его сам по этому процессу.

## 1. Разобраться
Определи, есть ли приложение, какие команды уже существуют и какие инструкции применимы. Не выполняй подготовительные действия, меняющие проект, только чтобы выяснить его структуру. Для существующего проекта проверь исходное состояние подходящими командами и запиши известные сбои.

## 2. Уточнить
Если задачи недостаточно, задай одну короткую группу из 3–5 существенных вопросов, допускается меньше. Для нового продукта обычно нужны: кто пользуется и зачем; обязательные сценарии первой версии; данные и доступ; где запускается; ограничения. Если ответы уже есть, переходи дальше. Блокирующие вопросы должны быть разрешены до зависящих от них решений.

## 3. Зафиксировать требования
Для нового проекта создай docs/SPEC.md: назначение, пользователи, сценарии, состав первой версии, что не входит, данные и роли при необходимости, платформа запуска и критерии приёмки с идентификаторами AC-01 и далее. Допущения явно отделяй от требований. Не подменяй выбор пользователя собственным удобством.

Для крупной функции в существующем приложении запиши необходимые требования прямо в её план; отдельную спецификацию создавай только при полезном объёме. Не заводи два конкурирующих источника требований.

## 4. Составить план
Используй docs/templates/PLAN.md как структуру, сохрани заполненный документ в docs/plans/<краткое-имя-задачи>.md. В каждом этапе укажи результат, затрагиваемые области, критерии и проверку. Порядок: минимально работающее сквозное решение, обязательные сценарии, ошибки и ограничения, завершение и документация. Стек выбирай по требованиям; для имеющегося приложения учитывай текущую архитектуру.

Команды проверок бери из реального проекта. Для пустого репозитория укажи их как запланированные до появления инструментов, а затем проверь и обнови. Не выдавай придуманные команды за выполненные.

## 5. Реализовать по этапам
При разрешённой реализации выполняй текущий этап: тест поведения или воспроизведение ошибки → ожидаемое падение → минимальная реализация → успешная проверка → улучшение без изменения поведения. Для UI, документации и конфигурации используй соразмерную проверку из AGENTS.md.

После этапа обновляй его статус и доказательства. Если меняется объём, обнови требования и объясни влияние. Внешние ограничения фиксируй как блокировки. Не начинай реализацию, если пользователь заказал только план.

## 6. Проверить целиком
Сверь результат с критериями приёмки. Запусти подходящие для проекта сборку, тесты и статические проверки. Пройди основной пользовательский сценарий; если это невозможно, укажи конкретную причину. Проверь изменения на случайные файлы и секреты. Для параллельных изменений проверяй объединённый результат.

## 7. Оставить точку продолжения
В плане запиши последний завершённый этап, состояние проверок, решения, блокировки и ближайшее действие. В README приложения должны быть фактические команды установки, настройки и запуска. Следующая задача начинается с состояния файлов и кода, а не с пересоздания процесса.
