# Правила работы Codex

Общайся с пользователем по-русски, объясняй решения простыми словами. Этот репозиторий может быть шаблоном или уже содержать приложение: сначала выясни его назначение по файлам и задаче пользователя. Не считай название репозитория техническим заданием.

## Начало задачи
- Прочитай применимые инструкции, проверь Git и относящиеся к задаче файлы. Сохраняй чужие изменения.
- Для нового проекта или крупной функции следуй PLANS.md. Для небольшой понятной правки достаточно краткого плана и подходящей проверки; не создавай пакет документов ради опечатки.
- Если пользователь просит только подготовить шаблон или план, ограничься этим. Не создавай приложение и не выбирай стек без задачи.
- Не предполагай доступ к прошлому чату. Восстанавливай состояние по спецификации, плану и фактическому коду.

## Планирование
- Задавай только вопросы, ответы на которые меняют поведение, архитектуру или объём задачи. Уже известное не переспрашивай. Некритичные пробелы закрывай явно записанными допущениями.
- Для нового продукта уточни назначение, пользователей, основные сценарии, данные и ограничения запуска. Предлагай простой вариант по умолчанию.
- Запиши требования и критерии приёмки до реализации. Если задача требует только планирования, остановись после подготовки плана. Если реализация уже разрешена, продолжай без повторного запроса разрешения.
- Существующий стек и соглашения сохраняй, если задача не требует их изменения. Не добавляй сервисы, зависимости или функции без причины.

## Реализация и проверки
- Работай небольшими завершёнными этапами. Для каждого этапа проверяй наблюдаемое поведение, затем обновляй план.
- Для новой логики и исправления ошибок сначала добавь содержательный тест. Зафиксируй ожидаемое падение из-за отсутствующей функции или воспроизведённой ошибки; затем реализуй и добейся прохождения. Ошибка установки, синтаксиса или тестового окружения не доказывает корректную красную фазу.
- Для визуальных изменений используй просмотр интерфейса, когда он доступен, и конкретный сценарий проверки. Для документации и простых настроек выбирай соразмерную проверку. Не требуй TDD там, где он не проверяет результат.
- Не ослабляй тесты и не удаляй проверки ради зелёного отчёта. Изменение ошибочного теста обоснуй требованием.
- После значимого изменения запускай относящиеся к нему проверки. В конце выполни применимые проверки проекта. Различай новые ошибки и ранее существовавшие.
- При сбое прочитай вывод, исправь причину и повтори нужную проверку. При внешней блокировке запиши её и точный следующий шаг; не имитируй успех.
- Не записывай в Git секреты, токены, реальные персональные данные и локальные файлы окружения. Примеры конфигурации должны содержать заглушки.

## Параллельная работа
- По умолчанию выполняй этапы последовательно. Используй делегирование только если оно разрешено пользователем и доступно в окружении.
- При параллельной реализации у каждой задачи должны быть границы файлов, контракт, критерии приёмки и отдельная ветка/рабочая копия. Не запускай несколько авторов в одном рабочем дереве.
- Если worktree недоступны, используй изолированные задачи/ветки окружения либо последовательную работу. Не обещай запуск дешёвых моделей или автоматическую оркестрацию без соответствующих инструментов.
- После объединения изменений повтори интеграционные проверки. Проверка отдельных веток не заменяет проверку объединённого результата.

## Завершение и передача
- Отметь в плане выполненное, оставшееся, решения и фактические результаты проверок. Оставь точный следующий шаг.
- В ответе сообщи: что изменилось; как проверено; что не удалось проверить; как запустить результат. Для интерфейса приложи изображение, если удалось получить его.
- Не заявляй «всё работает» без выполненных проверок. Не сливай PR, не развёртывай приложение и не выполняй необратимые операции без соответствующей задачи пользователя.

В облачной задаче используй существующую изолированную рабочую копию. Не создавай Git worktree без явного запроса пользователя.
